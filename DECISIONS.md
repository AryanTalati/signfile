# Decisions

Living record of what signfile includes, what it leaves out, and why. Updated whenever a decision is made or changed.

## Assumptions

- **Who the buyer is.** Astra AI is the first customer. The wider market is AI agencies, IT consultancies, dev shops and MSPs. Their clients are businesses, so the flow is B2B: the person we email may not be the authorized signer, the client's legal team may ask for changes, and the firm usually countersigns.
- **One agreement per File.** A File is one job or engagement for one client. Each File carries one agreement with up to two signing parties by default (client, then firm), in sequence. Templates may define more roles in signing order.
- **The agreement is unseen.** We will not see the MIND client agreement in advance. Detection must be generic (labels, underscore runs, drawn lines, layout heuristics) with a manual editor and an "append a signature page" fallback, so any PDF or DOCX can be signed.
- **Email link is enough identity.** Possession of the unique signing link, plus ESIGN/UETA consent and a full audit trail (IP, user agent, timestamps, hashes), is the identity standard. This is normal for commercial B2B agreements.
- **Email may not arrive.** Grading cannot depend on inbox delivery. The signing link is shown in the app right after sending, and every email is recorded in an in-app outbox.
- **Render free tier, kept awake.** We stay on Render's free tier (512 MB RAM, sleeps after 15 min idle, ~50 s cold start). A free external uptime pinger hits `/api/health` every 10 min. That keeps Render awake for the 3-minute test, and the DB query inside it keeps the Supabase free project from pausing after a week idle. One always-on service uses ~744 of the 750 free instance-hours a month. `/api/health?deep=1` converts a realistic multi-page DOCX and reports memory, to prove 512 MB is enough for LibreOffice. The pinger uses the light check only, so it doesn't spike memory every 10 min. **Measured on Render free (Nov 18):** a 4-page DOCX converts in 9.2 s (11.3 s before LibreOffice's profile was pre-built into the image) with the container peaking at 257 MB of 512 MB. Fine for the 3-minute test, but DOCX conversion must start immediately on upload and show progress.
- **App and DB in the same region.** Supabase is in Oregon (us-west-2). The Render service also runs in Oregon, the Blueprint default, now pinned with `region: oregon` in `render.yaml`. Measured on the live service: 3-4 ms per DB query.
- **Supabase session pooler (port 5432), not the transaction pooler (6543).** Originally the app used the transaction pooler with `prepare: false`. Under concurrent load (E2E suite, 9 workers), requests hung for 2 minutes until Postgres' statement timeout fired. `pg_stat_activity` showed backends `active` and waiting on `ClientRead`: Postgres was waiting mid-query for data the pooler never forwarded. The same suite over the session pooler passed 18/18 twice, in ~22 s instead of 3 minutes with failures. Session mode suits one long-lived server; the transaction pooler is built for serverless fan-out. `prepare: false` is kept since it's harmless.
- **Connection budget for session mode.** Each session-mode client connection holds one pooler server connection, and Supabase's default Pool Size is **15 per database/role**. Every one of our connections uses the `postgres` role. Postgres `max_connections` is 60; Supabase's own services use ~9. Budget: app pool **3** (`DB_POOL_MAX`) + 1 health-check connection = 4 per process. A Render deploy briefly runs old + new instances (8), plus a local dev server or Docker E2E run (4), plus 1-2 scripts = ~14, under 15. Idle connections close after 20 s and are recycled every 30 min. The Supabase dashboard/Studio connects directly and doesn't count. 3 connections handled the full parallel E2E suite (9 workers) without slowdown. If the instance count or pool size grows, raise Pool Size in Supabase's Database settings first.
- **Local dev and production share one database.** `npm run db:setup` migrates production, so migrations run before pushing code that needs them. Demo data is shared, which is fine for test data.
- **Incident (Nov 18): stuck wake-up on Render free.** After the instance slept, Render never restarted Node. There was no app output, and a redeploy of the same cached image also hung at "Deploying...". The same image started in 4.3 s locally under free-tier limits, and **Restart service** fixed it. Memory wasn't involved: 52 MB after startup, 209 MB peak during a DOCX conversion. Mitigation: the uptime pinger keeps the instance from sleeping. Runbook if it recurs: Render → Manual Deploy → Restart service.
- **Known limitation of the free hosting tier: 0.1 CPU.** Render's free instance has 0.1 CPU and 512 MB. Document processing (DOCX conversion ~9-10 s, PDF parsing, detection) is CPU-bound, so uploads are processed **one at a time**. Up to 3 more wait, and beyond that the upload page shows "Waiting for other documents to finish…" and retries for ~1 minute. Signing, viewing and the dashboard are light and unaffected. One person testing (the grading scenario) sees no queue; a team uploading several documents at the same moment would wait in line. **Scaling path:** (1) a larger Render instance (Starter 0.5 CPU or Standard 1 CPU) cuts conversion to ~1-2 s with no code change; (2) then move conversion + detection to a separate worker (an Inngest step or a dedicated Render worker service) so the web instance never does CPU-heavy work, and raise the queue limits. Testing follows the same constraint: the live site gets a short smoke test (1 worker, desktop); the full suite (desktop + phone, full parallelism) runs against the local Docker image.
- **AI costs are capped.** The README tells operators to set a monthly spend limit in the Anthropic console. If the limit is hit, the non-AI fallbacks take over.
- **Test data only.** Seed data, generated agreements and E2E fixtures use fictional names and example.com addresses.

## Included (and why)

### Phase 1: the core signing path (must be flawless)
| Feature | Why |
|---|---|
| Company signup, team members (admin/member), branding (name, logo, color) on emails + signing page | Sold to many firms, so multi-tenant from day one. Clients should see the firm's brand, not ours. |
| Upload PDF or DOCX; DOCX converted with LibreOffice headless | Firms keep agreements in Word. Converting server-side means one PDF pipeline. |
| Rule-based field detection (labels, underscore runs, drawn lines, role guess from headings) | Works with no AI and no network. The test agreement is unseen, so detection is generic. |
| Drag/resize review editor | Detection is never fully trusted. A human confirms before sending. |
| "Append a signature page" fallback | Scanned or unusual documents must still be signable. Prevents dead ends. |
| Create File: template, client legal name, signer, reference, firm-filled values (fee, start date…) | The firm fills the deal-specific details once, and they are stamped into the document. |
| Signing page: ESIGN/UETA consent, guided next field, draw/type signature, mobile-first | Legally sound consent, and most clients open links on phones. |
| Sequential signing (client, then firm countersign) | Matches how B2B agreements are executed. |
| Request changes (comment), decline (reason), forward to the authorized signer | B2B realities. Every one is logged, so there are no dead ends. |
| Deterministic seal: stamp values, append audit certificate, SHA-256 of original and final | Tamper evidence and a defensible record without depending on AI or third parties. |
| File dashboard (status, timeline, resend, void, download, copy link), outbox, public `/verify` | Operators need to see and act on every File. `/verify` lets anyone check a signed PDF. |
| Owner side of request changes: see the comment, upload a revised agreement as a new template version (fields carried over when pages match), resend on the same File; both versions in the timeline | Legal redlines are the most common B2B outcome. Without this loop, "request changes" would be a dead end. |
| `expired` File status with a branded expired page | Links shouldn't live forever. The client must know which firm to contact for a new link. |
| Certificate timestamps in UTC with each signer's local time + time zone | UTC is unambiguous for the record. Local time matches what the signer saw. |
| Edge cases: encrypted PDFs rejected clearly, large files, rotated pages, links opened twice, expired/voided links | "It works" means it works on documents and behaviour we didn't plan for. |
| Template + fields snapshotted into each File at send | Editing a template later must never change an agreement already sent. |

### Phase 2: automation and integration surface
CSV bulk create, REST API with hashed API keys, HMAC-signed webhooks, scheduled same-thread reminders that stop and notify the owner, Claude-assisted field labeling with confidence flags, Gmail send-as-firm and reply reading. *Why:* the brief says "automates it on every file". API + webhooks let any CRM integrate without us building connectors.

### Phase 3: reply handling with the owner in control
AI classifies replies (question, wants to talk, sign later, decline, out-of-office, unclear). Code routes each class. Every outbound message needs owner approval. Calendar slots are owner-approved. Drive archive and Slack notifications. *Why:* the slow part of manual signing is the back-and-forth, and firms will only trust it if they approve every message.

### Phase 4: product completeness
MIND sync on completion, onboarding checklist, pricing page (no billing), data export and per-client deletion, help page, E2E tests. *Why:* "close to a product a company could buy and run today".

### Engineering decisions
| Decision | Why |
|---|---|
| Next.js App Router + TypeScript, one Docker app on Render | One deployable. LibreOffice has to be inside the image. |
| Postgres on Supabase, Drizzle ORM + SQL migrations | Durable managed Postgres with pgvector available later. Drizzle is light, typed, and emits plain SQL migrations. |
| PDFs and logos in a private Supabase Storage bucket behind `storage.ts` | Render's disk is ephemeral. Keeping large blobs out of Postgres rows keeps the DB small. Same vendor as the DB, so one less account. |
| Hand-rolled email+password auth (argon2id via `@node-rs/argon2`, DB sessions, httpOnly cookie) | Small surface, and it fits the company/role model. The argon2 package ships prebuilt binaries, so the Docker build needs no native compilation. |
| Per-client deletion = hard delete of whole Files (files, recipients, events, outbox, documents, storage objects) via one privileged purge function; a PII-free `deletion_log` row records it | Redacting fields inside events would still leave names, emails and signatures in the sealed PDF and certificate, which can't be edited without breaking the hash. A record that's half redacted is neither private nor a valid audit trail. The insert-only trigger on `events` blocks UPDATE always and DELETE unless the purge function sets a transaction-local flag, so the audit log can't be edited piecemeal. The UI warns the firm to export first, since they may have their own retention duties. |
| Encrypted PDFs: **reject** ones that need a password to open, with a clear message; **accept** ones that open without a password but carry permission restrictions, stripping the restrictions (qpdf in the Docker image) before detection and stamping | Password-protected files can't be read without the password, and asking for it is a dead end for the firm. Permission-restricted PDFs open normally in every viewer and are common exports from contract tools, so rejecting them would surprise users. |
| Test agreements are generated, not hand-picked: `npm run gen:agreements` writes 12 fixtures + a ground-truth `manifest.json` (expected outcome, signer roles/pages, known traps) and self-checks each file | The detector is tested against layouts it wasn't designed around: table-cell signature blocks, dot leaders, drawn lines with labels below, two columns, initials boxes, scans, rotated pages, AcroForms, large files, encryption. Fixed-date output keeps regenerated files byte-identical. |
| RLS enabled on every table with **no policies**, and Supabase's `anon`/`authenticated` roles revoked | The server is the only client, and it connects as the table owner, so RLS doesn't affect it. If the Data API were ever switched on, nothing would be exposed. Tenant isolation is enforced in our query layer (`company_id` on every query). `npm run db:verify` checks this, plus the insert-only audit log and the purge function, against the real DB. |
| Health memory = non-reclaimable container memory (`anon + shmem + kernel` from cgroup `memory.stat`), not `memory.current` | `memory.current` includes page cache and drifted to the 512 MB limit without any OOM risk. The non-reclaimable figure shows real headroom: 164 MB peak during a DOCX conversion locally. |
| Public demo account (Astra AI, credentials on the login page and in the README) with a one-click "Log in to the demo" | Graders and prospects can test in seconds without signing up. `npm run seed` resets it. Everything in it is test data. |
| Login throttle keyed on IP+email (8 failures / 15 min) and IP (30), never email alone | Locking by email alone would let anyone lock out any account, including the public demo. Wrong-password responses take the same time whether or not the email exists (a dummy argon2 verify). |
| Signup retries with a new slug if two companies with the same name sign up at once | Found by the E2E suite (parallel desktop + phone signups). A unique-constraint race must not show users a generic error. |
| `purge_company()` deletes a whole company, the second way past the insert-only events trigger, and logs it to `deletion_log` (scope `company`, row counts only). `deletion_log.company_id` has **no** foreign key so the log outlives the company. `npm run purge:company` dry-runs by default, removes storage objects, and refuses the demo company | Needed for account deletion and to clean up E2E test companies from the shared DB. First used Nov 18 to remove an account created with real personal data on the live site. Afterwards, a hash-based scan of every text/JSON column found zero remaining copies of the address. |
| Client IP = Cloudflare's `CF-Connecting-IP` (fallback `True-Client-IP`), via one `getClientIp()` helper used by the login throttle, sessions and the audit trail. `X-Forwarded-For` is never trusted in production | Tested on the live Render URL: a client-sent `X-Forwarded-For: 1.2.3.4` stays as the *first* entry (`1.2.3.4, <client>, <Cloudflare edge>, <Render internal>`), so reading the first entry let anyone pick their IP and bypass the throttle. Cloudflare rejects requests that send their own `CF-Connecting-IP` (error 1000) and overwrites `True-Client-IP`. `X-Real-IP` isn't passed through. If no trusted header is present, the IP is recorded as unknown rather than guessed. Unit tests use the real header sets captured from production. |
| **Rule-based field detection** (no AI on Day 2): blanks (underscores, dot leaders, drawn lines split into table cells, empty boxes, form widgets) + labels (same phrase, left, grid row label, below, above, or a label with empty space beside it) + a signature-block filter + party roles (own label, "on behalf of", column heading, firm name, defined terms like `(the "Provider")`, unnamed upper-case headings) | Works offline and deterministically, and every field carries a confidence and a "why". Below 0.7 is flagged in the editor until a person confirms it. The signature-block filter is what keeps "Effective Date" and deal-term fill-ins out. |
| Detection is measured, not assumed: `npm run eval:detection` runs 12 generated + 3 real-world agreements (Common Paper PSA/CSA, Bonterms; CC BY / CC0) against a ground-truth manifest and writes `fixtures/detection-report.md` | Shows exactly where detection is weak. The tuned set is at 15/15 documents and 96/96 expected fields. A **held-out** test (YC SAFE, DOCX + PDF, run unchanged) found every signer field, but initially failed to separate the two parties, so the rules were generalised (see `fixtures/realworld/README.md`). Known weak spots: party names outside our vocabulary fall back to "first block = client" and are flagged; anything scanned gets "append a signature page". |
| Permission-only encrypted PDFs are decrypted with qpdf; damaged PDFs are repaired with qpdf; password-protected PDFs are rejected with instructions | qpdf is small (installed in the Docker image) and handles both cases deterministically. |
| A Docker `tools` target (same OS layer as production: LibreOffice + qpdf + fonts) runs the eval and scripts | Detection results match production exactly, without installing LibreOffice on developer machines. |
| Field editor: pick a type then click the page to add; drag to move; corner handle to resize; select then one click to retype or reassign; ⌘Z undo, ⌘D duplicate, arrows nudge, Delete removes; autosave | You asked for one-or-two-click edits, and it must work with zero detected fields. Every detected field shows its confidence; under 70% gets an amber dashed outline, ⚠ and a review list with "Looks right". |
| Saves carry the PDF's hash; the server rejects a save made against an older PDF, and autosave pauses during "append a signature page" | Found by E2E: an in-flight autosave of the empty field list could land after the append and wipe the new signature-page fields. |
| Signup transaction uses `lock_timeout = 5s` and retries | A signup must fail fast and retry, never hang on another transaction's lock. |
| Uploads are processed **one at a time** (3 may wait; more get "busy", which the upload page retries automatically for ~1 min), and abandoned uploads stop processing | Render free has 0.1 CPU. A live E2E run with 9 parallel workers queued so much conversion/parsing work that even logins timed out for an hour, while abandoned uploads kept running. Queueing keeps the site responsive for everyone. A grader uploading one document is unaffected. Live tests run with 2 workers; local/Docker runs keep full parallelism. |
| Signers always sign for themselves; no automatic signing on a company's behalf. Firm signing is fast instead: a **saved signature** (adopted once, with consent) and a per-template mode, **"Firm countersigns after the client"** (default) or **"Firm signs when sending"** (the authorized signer applies their saved signature at send time, logged as their own signing event, so the agreement completes when the client signs) | ESIGN/UETA require the signer's intent at the time of signing. An unattended company signature is weak evidence and something a client's legal team would push back on. Both modes keep a person in the loop while removing the countersign delay. Planned for Day 3. |
| **Body-text date blanks** (empty blank next to "as of", "dated", "date of", "Effective Date", "this ___ day of") become a date field at 0.60 confidence, always flagged for review. If "Effective Date" is mentioned it's the new **Agreement date** type (no signer: filled automatically with the date the last party signs); otherwise **Filled by you**. "this __ day of ____" is one field. "Date: ___" inside a signature block stays that signer's *date signed* | Real agreements carry the agreement date in the body, not in the signature block. Defaulting to automatic for the Effective Date means it can't be left blank or mistyped. Medium confidence because the wording varies, so a person confirms it. |
| **Filled blanks get no field**: a blank with a separate text item sitting on it (within ~7 pt of the line, covering ≥30% of it) is treated as filled; drawn lines with text on them were already treated as occupied | Seen on a real DocuSign-produced NDA, where the Effective Date was typed over its blank: adding a field there would overwrite a value the parties already agreed. The window is tight so the previous line of text (~12+ pt above) never counts, a regression caught by the eval. Fixtures: `pdf-date-blanks.pdf`, `pdf-prefilled-blanks.pdf`, `docx-filled-date.docx` (made-up names). |
| Signing links expire after **30 days** (per-company setting `link_expiry_days`) | Long enough for a client's legal review; short enough that a forgotten link doesn't stay live forever. An expired link shows a branded page with the firm's name and how to get a new one. |
| **Outbox-only email for now** (no provider key): every email is recorded in the outbox as "Not sent (outbox only)", and the signing link is shown on the File page right after sending | The test path and grading can't depend on email delivery. A Resend key (and later Gmail send-as-firm) switches the same outbox rows to real delivery without changing the flow. Decided Nov 19. |
| Sending snapshots the template's PDF (copied into the File's own storage folder) and fields into `file_documents` v1 | Template edits after sending never change an agreement already out for signature. |
| Signing page: link token is the only credential; ESIGN/UETA consent recorded (text, time, IP, UA) before the document is shown; the date signed is set by the server in the signer's browser time zone; submit is row-locked so a link opened twice or a double click can't sign twice; every non-signable state (signed, waiting, completed, expired, voided, replaced, declined, changes requested) has its own branded page | Each signing has to be defensible as evidence and never dead-end. `/sign/*` sends `Referrer-Policy: no-referrer` and `noindex` so tokens can't leak via Referer or search engines. |
| Signers type or draw; typed signatures render in a handwriting font to a PNG; once adopted, other signature/initials fields fill with one tap | Fast on a phone and still one deliberate action per field. |
| **Party roles are never guessed silently.** Every defined party in the preamble is tracked, including words outside our vocabulary ("Counterparty", "Investor"). If one party is clearly the firm or client (≥0.85), the others are the opposite side (0.8). "The Company" alone is ambiguous: the client only when the other party is clearly the firm. Unknown parties take the first-defined party as the firm, flagged at 0.5. Two separate signature blocks resolving to the same signer on weak evidence are split the same way and flagged. Hidden, zero-size and off-page form widgets (DocuSign leftovers) are ignored | Found in user testing (Nov 19) on a DocuSign-exported NDA: both visible blocks were detected as the client's (0.85, not flagged), and the firm's only "signature" was a zero-size widget at a page corner. No access issue: the signing page and server only ever accepted the signer's own fields. Fixture `pdf-unknown-parties.pdf` reproduces it with made-up names. |
| The submit endpoint **rejects** any value for a field that isn't the signer's own (422) rather than silently dropping it | Defense in depth: the UI never offers other signers' fields, but the server must not trust the client. Tested in the Docker suite and the live smoke test with a tampered request. |
| **Exact glyph geometry for every field.** Glyph positions come from the PDF text state (font size, text matrix, spacing, scaling) instead of spreading a text run's width over its characters. Blanks snap to their exact underscore/dot run. Each field box is fitted to the clear space: it rests on its own line, stays below the previous line (incl. a heading to its left), and stops at text on either side. Stamped values are bottom-aligned at ≤ 11 pt | Found in user testing (Nov 19): stamped signatures and text overlapped headings and labels on tightly set documents. Proportional estimates were 4-5 pt off on short labels and more on long sentences, and fixed 26 pt signature boxes reached into the line above. A regression check (unit tests + full eval, all pages of all 20 documents) fails if any field box overlaps a printed character; it flags the old detector on the new `pdf-compact-blocks.pdf` fixture (5 of 15 fields) and passes the new one (0). Sealing (step 6) uses the same boxes. |
| No hint text inside the document: an unsigned date field is an empty dashed box (the hint is a tooltip/aria-label), and the agreement date stays empty until the last party signs | Hint strings drawn into the page looked like agreement content to the other party. An E2E check fails if any hint string appears in the document area of either signer's view, and checks real values (date, name, signature image) appear once a party signs. |
| **Saved signature + one-click countersign** (built Nov 19): a firm user adopts a signature and initials once in Settings, with consent text that is logged. On their own signing link, while logged in as the named countersigner, "I agree, sign with my saved signature" records consent and signs on the server through the same locked path, plus a `signed_with_saved_signature` event. If a required field can't be pre-filled, it falls back to the normal flow. Anyone else opening the link gets the normal flow | One deliberate click, still the signer's own act. Entry points: "Countersign now" on the File page and a "Waiting for your countersignature" list on the dashboard. |
| **"Firm signs when sending"** (per template): the firm is signer 1 and the client signer 2. If the sender is the firm signer and has a saved signature, a "Sign now with my saved signature" checkbox (checked by default, with consent text) signs during sending. Otherwise the File waits on the firm signer ("Sign to send" email) and goes to the client once they sign. Only the named firm signer can sign now | The agreement completes the moment the client signs, with no countersign wait. Nobody's signature is ever applied without them acting. Status labels name who the File is waiting on. |
| **Sealing** runs in the same request as the last signature, deterministic and exactly once (File row lock). It stamps every value with the field boxes from detection, converted for page rotation: text bottom-aligned at ≤ 11 pt and shrunk to fit, signatures/initials as images anchored bottom-left, checkboxes as ✔, the agreement date as the completion date in the last signer's time zone. Existing form fields are flattened, and an audit certificate is appended | The signed PDF must look right on the first pass and be self-contained evidence. Before stamping, the stored agreement's SHA-256 is checked. The certificate lists the File ID, document and version, parties, source + agreement SHA-256, and for each signer: role, email, title, consent and signing times in UTC plus local time and IANA zone, IP, browser, signature image; then the full event log. The final PDF's own hash can't be printed inside itself, so it's stored on the File and checked by `/verify`. If sealing fails, the signature is never lost: the File page offers "Retry sealing" and downloads seal on demand. |
| **`/verify`** (public): upload a PDF, its SHA-256 is compared with sealed Files and agreement originals; the file isn't stored, and only the firm, completion date and signer count are shown | Anyone (a client's lawyer, an auditor) can check a copy is unaltered without an account. |
| Sealing E2E compares the sealed PDF with the original glyph-by-glyph: every stamped character must sit clear of printed text, real values must be present, no hint strings anywhere, and `/verify` must accept the copy but reject a one-byte change. The live smoke test runs the full path (send, sign, countersign, seal, verify) | Proves the output, not just the UI. |
| **Stamping always fits each field to the clear space on the actual page** (`fitToPage`, shared by sealing and the signing preview), whatever the field's origin | User testing (Nov 19): a File sent *before* the geometry fix kept its old boxes in its snapshot (snapshots are frozen by design), so its sealed PDF still had values over "of", "CLIENT" and "RIVERTON…". Fixing detection alone couldn't help Files already out for signature. Re-fitting at stamping time can't change what a party agreed to: only where a value sits inside its own blank. Verified on that exact File: the stored sealed copy has 29 stamped characters and 4 signature images on printed text, a fresh seal with the new code has 0 and 0. Image placements are now extracted too, so stamped signatures are checked as well as text. |
| Sealing builds the PDF **outside** the database transaction; a short row-locked transaction records it (a concurrent duplicate deletes its own upload) | Holding a transaction (and one of 3 pooled connections) during download/layout/stamping/upload starved the pool under concurrent completions (E2E timeouts). Exactly-once is kept by the re-check under the lock. |
| **Completed, sealed Files are immutable.** A sealed PDF and its recorded SHA-256 are never replaced or re-sealed, even after a rendering fix; corrections happen by sending a new File | A sealed copy is what the parties received and what `/verify` confirms. Replacing it would make earlier copies fail verification and undermine the audit trail. Applied Nov 19 to File `4e7959eb` (sealed before the stamping fit fix): left as is. Fixes apply to Files sealed from then on, including Files sent earlier but sealed later. |
| UI timestamps in the **viewer's local time zone** (client-side after mount); the audit trail and certificate stay in **UTC** | People read times in their own zone; evidence stays unambiguous. The signer's own date-signed field previews today's date in their local format, greyed, with the tooltip "Added automatically when you sign". It's display only and never in submitted values, so it can't reach stamping; the sealed PDF uses the server's signing timestamp. |
| **File actions** (built Nov 19): an **Outbox** page lists every generated email, opening to the rendered email (sandboxed) and its links. **Void** works on any File not completed: a reason is required and logged, all open links are revoked and show "This agreement was voided", and everyone who got a link is emailed. **Resend** goes to whoever's turn it is, at most once per 10 minutes per signer (the original send counts) | Firms need to correct mistakes and nudge signers without leaving the app; rate limits stop accidental spam. The void reason stays internal: signers aren't shown it. |
| **Timeline and certificate use one plain-English label table** for every event type ("Viewed by {name}", "{name} agreed to sign electronically"…). A unit test scans the code for emitted event types and fails if any lacks a label; unknown types never render as raw dotted names | Raw names like `recipient.viewed` read as broken to firms and their clients. |
| Emails name **people, not companies, for who did something**: "Countersign: {signer} ({client company}) signed …", and the client's sign request after the firm signs first comes from the firm signer by name. The client company is added only if entered and it isn't the firm's own name (compared ignoring case, punctuation and LLC/Inc/Ltd suffixes) | User report (Nov 20): the countersign subject named the firm ("Acme Rentals LLC signed") because it used the File's client-company field rather than the signer. All templates checked; unit tests cover it. |
| **Email via the Gmail API over HTTPS** (plain `fetch`: refresh token → cached access token → `users.messages.send` with base64url UTF-8 MIME; the firm's name as display name; the sealed PDF attached to signed-copy emails) | Render's free tier blocks outbound SMTP. No SDK keeps the image small. Credentials only come from env and never appear in logs, errors or the database. |
| **The outbox stays the audit log**: every email is saved first, then delivered after the transaction commits, in the background. Statuses: `sent`, `failed` (error text, no secrets, Retry button), `captured` (sending off in this environment, or a reserved test domain like example.com) and `queued`. A sweep on the health ping retries anything left queued | Delivery must never block or break signing: a Gmail outage leaves rows "failed" and the signing link is still on the File page. Test addresses are never sent, so the live smoke test can't email anyone. The Docker E2E suite runs with Gmail disabled. |
| Public fully-signed page shows "Signed with SignFile · Verify a document" (link to `/verify` only, nothing to the firm's dashboard or login), and "A copy has been emailed to everyone who signed" only if every signed-copy email was actually sent. `/privacy`: a test project, use test data only, demo data deletable on request | Never claim an email went out when it didn't; don't expose firm-only pages to clients. |
| **Known limitation: duplicate emails are possible.** Gmail's send API has no idempotency key. If Gmail accepts a message but the response is lost (timeout/network), the row shows "failed" and a manual Retry sends it again. If the server dies after Gmail accepted but before the row is updated, the sweep can resend (≤ 3 attempts) | Accepted for now. The fix, separating "definitely failed" from "may have been sent" (and later Message-ID lookup with a read scope), is planned, not built. |
| **Known limitation: emails may land in spam.** They're sent from a free Gmail address, without the firm's own domain, SPF/DKIM/DMARC alignment or a sending reputation | Fine for a demo. A production setup would send from a verified domain (Google Workspace or a transactional provider with DKIM) per firm. |
| **No "reject the change request / resume signing" path** (deliberate omission). After "Request changes" or "Decline", the only firm action is "Upload revised version and resend" | Negotiation happens outside the tool (email, calls, redlines). The tool's job is to get the agreed version signed, not to host the back-and-forth. |
| **Revised versions** (after Decline / Request changes): the upload becomes a hidden, File-specific template (`templates.revision_for_file_id`), so one client's negotiation never changes the firm's standard template. It goes through the same detection and editor, then "Resend revised version" snapshots it as version n+1. The old version is marked superseded (kept) and its open links revoked. The same people sign again in the same roles: the first signer gets a "revised version" email (with "sign this version again" if they had signed), later signers a notice | Signatures don't carry over between versions: a signer must see and sign the exact text that's sealed. The certificate covers only the signed version (events from the last revision onward); the File timeline keeps the full history, with a Versions card. |
| Decline emails **every party on the File** (all signers + the firm's owner/signers, deduped); Request changes emails the firm only | Everyone who might act on a declined agreement needs to know signing stopped. A change request is a message to the sender. |
| **Fast revisions**: signers, order, titles, emails, client name, reference and "Filled by you" values carry over (it's the same File). Fields are re-detected on the new document and matched to the previous version's by **type + signer role + anchor text** (words to the left on the row and just above), not position; matched fields keep the old label, required flag and fill key. If every previous field matches with high confidence and nothing is new, the upload goes straight to "N of N fields matched. Nothing to review" + one-click send. Otherwise only the new / low-confidence fields are listed, and "Review" opens the editor showing just those | Most revisions change wording, not the signing blocks, so the firm shouldn't re-review everything. Flagged fields must be confirmed before sending. |
| "What changed?" note (prefilled with the signer's request) goes into the new-version emails and the `file.revised` audit event / timeline, **but not the sealed certificate** | The note can quote the earlier version's change request; the certificate describes only the signed version. |
| **Reminders and expiry** run on the `/api/health` ping sweep (single-flight, at most once a minute). Per-firm settings (default: 2 and 5 days after it becomes a signer's turn, plus 2 days before expiry). Each reminder is an outbox row tagged with its schedule slot; a unique index on (signer, slot) means a slot is sent at most once even if sweeps overlap. Only the latest due slot is sent (a sweep that was down doesn't send a burst), and a signer emailed in the last 20 h isn't reminded yet | All state in Postgres; idempotent by construction; no Inngest needed for a fixed schedule. |
| The sweep runs **only with an explicit `ENABLE_SWEEP=1`** (set on Render only) and never with `E2E_HOOKS=1`. Changed Nov 20 from "whenever Gmail is configured" | Local, Docker and Render share one database, and local dev has the Gmail vars too: a dev sweep could send reminders or expire Files. An explicit opt-in can't be triggered by accident. Expiry still happens on link open everywhere. |
| Expiry emails the File's owner (or the first admin). "Extend and resend" on an Expired File sets a new expiry from the firm's setting, restarts reminders and resends | An expired File was a dead end; the firm needs one click to recover. |
| Mocked time in tests: `POST /api/test/automations {fileId, now}` runs the same sweep for one of the caller's Files at a chosen time; exists only with `E2E_HOOKS=1` (Docker test run), 404 otherwise | Tests the real sweep and real DB constraints without touching the clock or waiting days. |
| **Auto-countersign** is a per-user setting, not firm-wide: only the countersigner can turn it on, for their own saved signature, after an explicit authorization (text kept in the audit log with IP/UA). Off by default; removing the saved signature turns it off. Applies only when the firm signer is the last one left | The brief asked for a firm setting, but an admin switching it on for a partner would be signing on their behalf. A standing instruction from the signer is their own act of signing. |
| An automatic countersign is recorded as the signer's own signing (consent, values, `recipient.signed`) plus `recipient.auto_countersigned` ("Countersigned automatically with X's saved signature (authorized date)"). Its IP is the one from which they authorized it; the user agent says "Automatic countersign authorized …" | Nobody was at a browser when it was applied: recording the client's IP or a server IP as the firm signer's would be misleading. |
| If auto-countersign can't apply (turned off meanwhile, a firm field that needs typing), the countersigner gets the normal "please countersign" email and the timeline says why | Never a dead end; never a guess. |
| **"Send immediately"** on File creation (default on in the form and in the schema, so CSV/API creation later sends unless told not to). Off = a **Draft**: signers and links exist but nothing is live, nothing is emailed, no expiry, no reminders. "Send now" on the File runs the same send step as create-and-send. "Firm signs when sending" only applies when sending immediately | Firms sometimes prepare a File before the deal is final. One shared send step keeps drafts and immediate sends identical (same events, emails, expiry). |
| Signing page prefills name and title from the File (still editable; editing one copy updates the others). A changed prefilled value is logged ("Name changed from X to Y"); a blank title stays blank | One click for the usual case, and the audit trail shows any difference between who the firm named and what the signer wrote. |
| The certificate's **Title** is the one the signer entered in their Title field in the signed document; no Title field = no title on the certificate | The File-form or profile title can contradict the signed document (a profile "CEO" vs "Managing Partner" printed in the agreement). Guessing a printed title from the page would be a guess. |
| **Firm time zone** (companies.timezone, from the browser at signup, editable in Settings). Certificate times read "UTC / local": signers in their own browser zone, the completion line, event log and signers without a zone (automatic countersigns) in the firm's | UTC stays primary for proof; the local time is what people check against. Null zone = UTC only, never a guessed zone. |
| An automatic countersign's certificate block says "Method: Automatic countersign using saved signature" and "Authorized: <time>, IP, browser" (from when they turned it on); "Agreed to e-sign" is that authorization time, and the event log says consent was given in advance | That is when and where the signer actually agreed; the signing moment is the system acting on their instruction. Recording it as a fresh consent would misstate what happened. |
| Every AI feature has a non-AI fallback (`AI_ENABLED=false` or no key), and the test suite runs with AI disabled | The product must work if the API is down, the key is missing or the spend limit is hit. |
| Event-driven workflow (Inngest) with AI steps, no agents | Predictable, auditable, retryable. State lives in Postgres, not in prompts. |
| Sealing runs synchronously in the final-signature request | The critical path must not depend on a queue or integration being up. |
| All LLM calls through one wrapper with zod-validated structured outputs | Provider swappable, outputs validated, and easy to disable (rule-based fallback). |
| Field coordinates stored normalized (0–1) relative to the page as displayed | Survives rotated pages and any rendering scale. Converted to PDF space only when stamping. |
| Signing tokens: 32 random bytes (base64url), stored in DB, unique index; a "copy link" re-reads them | The firm needs to copy the link again later. Tokens are revoked on void, forward or completion. |
| Outbox written before any send attempt; sending is best-effort with retries | Every email is visible in-app even if the provider fails. |
| Hash both the uploaded original (DOCX or PDF) and the PDF that was signed, plus the final sealed PDF | The certificate proves which source document was signed. |

## Left out (and why)

| Left out | Why |
|---|---|
| SMS / WhatsApp | B2B agreements are sent and signed by email. Adds cost, compliance work and phone-number collection for little gain. |
| Native CRM connectors (HubSpot, Salesforce…) | The REST API + signed webhooks (+ Zapier on top of them) cover every CRM without one-off connectors. |
| Microsoft Teams / Outlook | Time-boxed to one ecosystem (Google + Slack). The integration layer is pluggable, so these can be added later. |
| Stripe billing | Pricing page only. Billing doesn't help get an agreement signed, and it adds risk to a 7-day build. |
| Identity verification beyond the email link (ID scan, KBA, SMS OTP) | Not needed for commercial B2B agreements under ESIGN/UETA. The audit trail covers it. |
| SSO (SAML/OIDC) | Enterprise feature. Small firms use email+password. |
| Autonomous / multi-agent design | Not predictable or auditable enough for legal documents. Code and humans decide next steps. |
| n8n / Zapier as the core | The workflow must be in our code and DB to be reliable and multi-tenant. Zapier can sit on top of webhooks. |
| AI memory of client conversations | Privacy risk and prompt bloat. Each AI call gets a small fixed input about one File. |
| AI explaining contract terms directly to clients | Liability: that's legal advice. Drafts go to the owner, cite a clause, and need approval. |
| In-app editing of agreement text | Agreements are drafted in Word. Editing PDFs breaks fidelity and the hash chain. Changes are requested, then a new version is uploaded. |
| Certificate-based PDF digital signature (PAdES) | Needs a trusted CA certificate. A self-signed one shows warnings in Acrobat. SHA-256 + `/verify` + the audit certificate give tamper evidence. *Revisit if ahead.* |
